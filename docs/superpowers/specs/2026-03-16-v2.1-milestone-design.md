# v2.1 Milestone Design Spec

**Date:** 2026-03-16
**Scope:** Settings screen, REPEAT step support, timer controls redesign, history screen
**Deferred to v2.2:** Overview screen (workflow graph visualization), waiting steps UI, QR code scanner

## Phase 1: Settings Screen + Swipe-to-Delete UX

### Settings Screen

Expand `SettingsScreen.tsx` from two toggles to a full settings panel with grouped sections.

**Sections and controls:**

1. **Appearance**
   - Theme toggle: Light / Dark (localStorage key `trajectory-theme`, default `light`)
   - Apply via CSS custom properties on `:root` / `[data-theme="dark"]`

2. **Notifications**
   - Toggle: "Notify on new active steps" (localStorage key `trajectory-notify-steps`, default `false`)
   - On enable, request `Notification.permission` via browser API
   - If user denies permission, revert toggle to off and show inline message: "Notification permission denied. Enable in browser settings."
   - When a step enters EXECUTING state and the tab is not focused, fire a browser notification

3. **Confirmations**
   - Toggle: Confirm delete loaded workflows (existing — `trajectory-confirm-delete-loaded`, default `true`)
   - Toggle: Confirm delete completed workflows (existing — `trajectory-confirm-delete-completed`, default `false`)

4. **Data Management**
   - Button: "Clear All History" — removes all completed workflows via `manager.clearCompleted()`
   - Button: "Release All Resources" — new method chain: `WorkflowManager.releaseAllResources()` → iterates active coordinators → `WorkflowCoordinator.releaseAllResources()` → `WorkflowEngine.releaseAllResources()` (new public method) → `resourceManager.releaseAll(instanceId)` (existing method)

Each setting uses the existing `useLocalStorage` hook pattern.

**Theme implementation:**

Define CSS custom properties for both themes in a new `theme.css` file:
```
:root, [data-theme="light"] { --bg: #fff; --text: #1a1a2e; --card-bg: #f8f9fa; ... }
[data-theme="dark"] { --bg: #1a1a2e; --text: #e0e0e0; --card-bg: #2a2a3e; ... }
```

Apply `data-theme` attribute on `<html>` element from App.tsx based on localStorage value.

**Theme migration scope:** Migrate colors in these CSS module files to use CSS variables:
- `HomeScreen.module.css`, `ActiveScreen.module.css`, `SettingsScreen.module.css`, `HistoryScreen.module.css`
- `DeviceFrame.module.css`, `TitleBar.module.css`, `AppShell.module.css`
- `App.css` (global styles, form elements)

Non-screen CSS files (element-specific styles) can be migrated incrementally in later phases.

**Known limitation:** Theme changes in one browser tab do not propagate to other open tabs. Acceptable for v2.1.

### Swipe-to-Delete UX Redesign

Replace current text-button swipe reveal with a polished iOS-style pattern:

- Swipe left on a loaded or completed workflow item reveals a **red box with a trash can icon** sliding in from the right
- The red box occupies the right portion of the row (approximately 80px wide)
- The workflow item slides left to reveal the delete zone
- Tapping the red zone triggers delete (with confirmation if enabled in settings)
- Tapping anywhere else or swiping back cancels
- Use CSS `transform: translateX()` with transition for smooth animation
- Touch threshold: 80px horizontal swipe to trigger reveal (matches existing code)

## Phase 2: Timer Controls Redesign

Replace the current timer UI with a clean, phone-friendly design.

**Current problems:** Controls are bare unstyled buttons ("Stop", "Reset", "Continue") that look out of place on mobile.

**New design:**

- Large centered time display (monospace, ~32px font)
- Timer label above the time
- Control buttons as **pill-shaped icon+text buttons** below the display:
  - Play/Pause toggle (single button, Lucide `Play`/`Pause` icon, changes based on state)
  - Reset button (Lucide `RotateCcw` icon)
- All buttons minimum 44px touch target
- Uses theme CSS variables for colors
- Countdown: linear progress bar below the time showing remaining fraction
- Countdown at zero: display text turns red with a CSS `@keyframes` pulse animation (opacity oscillation)
- `blockDone` behavior: when `blockDone === true` on the timer element, the step's Done/Continue button should be disabled until the countdown reaches zero. This is communicated via `onFormChange(el.fieldName + '__blocked', elapsed < el.durationSeconds)` and checked by the parent form's submit/button logic.

**Files touched:**
- Modify: `TimerElement.tsx` — redesign layout and controls
- Create: `TimerElement.module.css` — new timer styles using theme variables

## Phase 3: REPEAT Step Support

### Engine Changes

**New top-level engine method (not via submitAction):**

REPEAT does not complete a step — it rewinds execution. This is fundamentally different from `submitAction` which transitions a step to COMPLETED. Therefore, REPEAT is a new public method on `WorkflowEngine`:

```typescript
repeatToSteps(targetOids: string[]): void
```

**New engine method: `getCompletedSteps()`**
Returns all steps that have reached COMPLETED state, in completion order, with their spec data. Used by the UI to populate the REPEAT step picker. Excludes auto-completing step types (START, END, PARALLEL, WAIT ALL, WAIT ANY).

```typescript
interface CompletedStepInfo {
  oid: string;
  localId: string;
  stepType: string;
  description: string;
  completedOrder: number;  // from trace
}
```

**Repeat execution logic in `repeatToSteps()`:**

1. Validate `targetOids` — all must be in COMPLETED state
2. Build a forward adjacency map from `this.connections`
3. For each target step, BFS forward through the adjacency map to collect all downstream steps up to and including current active steps
4. For each step in the reset set:
   - Reset `step.state` to `IDLE`
   - Remove from `routingContext`
   - Remove from `waitAllTracking`
   - Remove from `pendingUserSteps`
   - Remove from `pendingResources`
   - Remove from `stepParameterSnapshots`
   - Remove from `completionQueue`
5. Re-activate target steps (same logic as `activateStep()`)
6. Run `drainCompletionQueue()` to process any auto-completing steps
7. Workflow state remains RUNNING

**Child workflow scoping:** REPEAT does not cross child workflow boundaries. Steps inside a WORKFLOW PROXY child engine are not visible in `getCompletedSteps()`. If a REPEAT target is a WORKFLOW PROXY step itself, the entire child workflow is re-executed from its START.

**Branch safety check: `checkRepeatSafety(targetOids: string[]): string[]`**
Returns an array of warning strings for the UI:
- Build backward adjacency map from connections
- Walk backward from current active step(s) through connections
- If a target step is NOT on a direct ancestor chain (i.e., is behind a PARALLEL/WAIT ALL boundary), return a warning: "Step {description} is on a different branch — workflow may not execute correctly"
- The UI displays warnings but does NOT block the repeat — user decides

### Coordinator Changes

- Add `repeatToSteps(targetOids)` method that delegates to engine
- Add `getCompletedSteps()` method that delegates to engine
- Add `checkRepeatSafety(targetOids)` method that delegates to engine

### UI Changes

**REPEAT button:** Add a "Repeat" button to `ActiveStepCard.tsx` action bar. Only shown when `getCompletedSteps()` returns non-empty. Uses Lucide `RotateCcw` icon.

**Step picker dialog (`RepeatStepPicker.tsx`):**
- Modal overlay listing completed steps in execution order
- Each row shows: step type icon, description/label, local_id
- Steps on a different parallel branch show a warning badge (yellow triangle + tooltip)
- Checkbox selection (multi-select for parallel restarts)
- "Confirm Repeat" button at bottom, disabled until at least one step selected
- Warning banner at top if any selected steps have safety warnings

**KMP engine impact:** Adding `repeatToSteps` and `getCompletedSteps` to the TS engine will break KMP parity. KMP updates are deferred to v2.2 — the KMP adapter in `KmpEngineAdapter.ts` will stub these methods with no-ops/empty returns.

### Test Plan

New engine tests for REPEAT:
- `repeat-linear`: repeat a completed step in a linear chain, verify downstream steps reset and re-execute
- `repeat-parallel-safe`: repeat a step on the same branch as active step (no warning)
- `repeat-parallel-warn`: repeat a step on a different branch (warning returned)
- `repeat-workflow-proxy`: repeat a WORKFLOW PROXY step, verify child re-executes from START
- `repeat-double`: repeat the same step twice in succession
- `repeat-invalid`: repeat a step that is not COMPLETED (error/no-op)

## Phase 4: History Screen

Replace the placeholder `HistoryScreen.tsx` with a reverse-chronological step completion log across all workflows.

### Prerequisites

1. **Add `timestamp` to TraceEntry** (engine change): Currently TraceEntry has `step_oid`, `state`, `order`, `after_action`, `error`. Add `timestamp: number` (Date.now() at recording time). This is a standalone engine change, not dependent on REPEAT.

2. **Add `stepParams` to CompletedWorkflow**: Currently `CompletedWorkflow` in `engines/web-ui/src/manager/types.ts` stores `trace` and `properties` but NOT per-step parameter snapshots. Add `stepParams: Record<string, { inputParameters: Record<string, string>; outputParameters: Record<string, string>; description: string; label: string; stepType: string }>` to `CompletedWorkflow`, and capture it from the coordinator snapshot in `WorkflowManager.completeWorkflow()` before calling `coordinator.reset()`.

### Data Model

**Enriched history entry (derived at render time, not stored):**
```typescript
interface HistoryEntry {
  workflowId: string;
  workflowName: string;
  stepOid: string;
  stepType: string;
  description: string;
  completedAt: number;       // from TraceEntry.timestamp
  inputParameters: Record<string, string>;
  outputParameters: Record<string, string>;
}
```

Built by flattening all `CompletedWorkflow` objects: for each trace entry where `state === 'COMPLETED'`, join with `stepParams[step_oid]` for parameters.

### UI Layout

**Main view:**
- Reverse-chronological list of completed steps (newest on top)
- Each row: workflow name badge (colored pill), step type icon, description, relative time ("2m ago" for < 1hr, absolute timestamp after)
- No virtualization in v2.1 (defer if performance issues arise)

**Filter controls (top bar):**
- Date range filter: "Today", "Last 7 days", "All" (pill buttons)
- Workflow filter: dropdown with "All Workflows" + each workflow name
- Filters combine (AND)

**Step detail popup:**
- Tap a step row to show a popup overlay
- Shows: completion timestamp (absolute), step type, description
- Input parameters table (name : value)
- Output parameters table (name : value)
- "Close" button or tap-outside-to-dismiss

### Data Persistence

Persist completed workflows to localStorage for history survival across page reloads:
- localStorage key: `trajectory-completed-history`
- Cap at 50 most recent workflows
- Serialize on each workflow completion; load on WorkflowManager construction
- Large traces: cap at 500 trace entries per workflow to bound localStorage usage

**Files touched:**
- Modify: `engines/web/src/types.ts` — add `timestamp` to TraceEntry
- Modify: `engines/web/src/engine.ts` — populate `Date.now()` on trace entries
- Modify: `engines/web-ui/src/manager/types.ts` — add `stepParams` to CompletedWorkflow
- Modify: `WorkflowManager.ts` — capture stepParams on completion, localStorage persistence
- Rewrite: `HistoryScreen.tsx` — full implementation
- Create: `HistoryScreen.module.css` — styles
- Create: `StepDetailPopup.tsx` — step detail overlay
- Create: `StepDetailPopup.module.css` — popup styles

## Execution Order

```
Phase 1 (Settings + Swipe UX)  →  Phase 2 (Timer)  →  Phase 3 (REPEAT)  →  Phase 4 (History)
```

Phase 1 establishes the theme system all subsequent phases use. Phase 2 is a small independent UI fix. Phase 3 is the heaviest engine work. Phase 4 has two engine prerequisites (TraceEntry timestamps + CompletedWorkflow.stepParams) that should be implemented at the start of Phase 4, independent of REPEAT.
