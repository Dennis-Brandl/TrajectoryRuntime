<decisions_made>

- **Synchronous resource management** — No async/await; fits within existing synchronous engine drain loop
- **flushGranted() pull pattern** — Avoids re-entrancy issues in the synchronous completion drain
- **acquiredByRequesterId map** — Tracks which requesterId acquired each resource to support cross-step acquire/release (Acquire on step A, Release on step B)
- **Auto-create ResourceManager in engine.start()** — Detects resources from workflow specs, step commands, and child workflow commands
- **Environment loading in WorkflowCoordinator** — Coordinator creates ResourceManager and loads environments before passing to engine, keeping engine constructor clean
- **adm-zip dependency** — Added for server-side .WFmasterX ZIP extraction; web-ui uses JSZip (already present)

<context>
The resource management system is the first major feature after Phase 3 (UI Screens). It implements Trajectory's 5 resource types: binary exclusive use, binary shared use with pool limits, countable use with pool limits, named pool, and sync. Resources can be workflow-scoped (defined in the workflow JSON) or environment-scoped (defined in .WFenvir files inside .WFmasterX packages). The engine processes resource commands during step activation (Acquire, Send, Receive, Synchronize) and step completion (Release). Steps blocked on resources enter WAITING state and are resumed via flushGranted() after releases.
</context>
